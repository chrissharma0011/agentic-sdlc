# Testing Approach

Testing in this project happens at **two distinct levels**, plus a **runtime verification layer** that is part of the pipeline itself. This document describes each, how to run them, and their limitations.

---

## 1. Engine tests (the orchestrator)

The thing being graded is the orchestrator, so its core control logic has a dedicated test suite that runs **without an API key** — it uses synthetic in-memory nodes, so it is fast and deterministic.

**Run:**
```bash
python3 tests/test_engine.py
```

**What it verifies (`tests/test_engine.py`):**

- **Concurrent fork-join execution.** A graph with two same-group nodes (`implement ∥ test`) runs them concurrently and synchronizes at `verify`; the test asserts the `parallel_start` / `parallel_join` events fire and all tasks complete.
- **Dynamic re-planning.** A node that fails verification triggers the controller to inject a `repair` task, re-route the graph, and loop back; the test asserts a `replan_injected` event occurs, the `repair` task appears in the graph, and `verify` reaches `done`.
- **Closed human-approval loop.** After retries are exhausted and a human approves at the escalation gate, the run **resumes to completion** rather than halting; the test asserts the `human_approved_fix` event fires and the run finishes with the failed node done.

These three cover the behaviors most likely to break and hardest to eyeball: concurrency, self-modifying graphs, and human-in-the-loop resumption.

---

## 2. Fixture tests (the generated shortener)

The generated URL shortener ships with its own pytest suite (`shortener/test_app.py`) covering the shorten, redirect, and stats endpoints. These are generated by the pipeline's Test node and can also be run directly:

```bash
pytest shortener/test_app.py
```

---

## 3. Runtime verification (part of the pipeline)

Beyond the two static suites, **verification is a first-class step inside every pipeline run.** The Verify node (`nodes/agents.py`) does not merely check that code exists — it **executes real pytest** against the generated code in an isolated temporary directory (`_run_pytest`), and gates on the actual pass/fail result.

If the tests fail, the node **self-heals**: it repairs the code toward the frozen tests and re-runs pytest, up to a repair budget (`REPAIR_BUDGET = 3`). If it still cannot pass, control returns to the controller, which may re-plan (inject a repair task) or escalate to a human. This means every run is validated by real test execution, not by heuristics.

---

## How the levels fit together

| Level | What it tests | Needs API key | When it runs |
|---|---|---|---|
| Engine tests | Orchestrator control logic (gates, parallelism, re-planning, approval resume) | No | On demand (`tests/test_engine.py`) |
| Fixture tests | The generated shortener's endpoints | No | On demand (`pytest shortener/test_app.py`) |
| Runtime verification | The freshly generated code, every run | Yes (full pipeline) | Automatically, inside every `build.py` run |

---

## Verifying crash recovery (offline)

Crash recovery can be checked without an API key by killing a run mid-way and
re-invoking it: events are flushed to `runs/<run_id>/events.jsonl` as they
happen, so on restart the log replays and the run resumes from where it stopped,
re-running only the interrupted node. The engine test suite covers the resume
logic (completed stages are marked done and skipped).

## Limitations & honest notes

- **Engine tests use synthetic nodes, not live LLMs.** This is deliberate: it isolates the *control logic* from LLM non-determinism so the tests are deterministic and fast. It does mean the engine tests do not exercise real prompt behavior — that is covered by running the scenarios end-to-end.
- **LLM output is non-deterministic.** The same requirement can produce passing code on one run and failing code on another. The runtime verification + repair + re-planning + escalation layers exist precisely to manage this; a run that fails and then recovers (or escalates honestly) is the system behaving correctly, not a test failure.
- **Fixture test coverage is scoped.** The generated shortener's tests cover the core endpoints, not exhaustive edge cases — appropriate for a prototype fixture whose purpose is to exercise the orchestrator.
- **No CI configured.** Tests are run manually. Adding a CI workflow (run engine + fixture tests on push) would be a natural next step but is out of scope for this prototype.
